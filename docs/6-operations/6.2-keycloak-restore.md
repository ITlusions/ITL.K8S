# 6.2 Keycloak restore plan

Restore plan for the Keycloak realm `itlusions` (`sts.itlusions.com`). There are two restore paths:

- **Database restore (preferred):** restores everything, including password hashes, MFA credentials, sessions, and the realm signing keys. Clients keep working without changes.
- **Realm import (fallback):** rebuilds the realm from the JSON exports. Users must reset passwords, MFA must be re-enrolled, and every client must pick up new signing keys.

The dump's PostgreSQL major version must match the restore target, which is 15 here. Restoring into a newer major version needs the dump to be replayed with `pg_restore`, and a major-version upgrade plan.

Note that the cluster also has a CloudNativePG PostgreSQL 17.0 image (`ghcr.io/cloudnative-pg/postgresql:17.0`) on `nwa02` and `nwa03`, and a `bitnami/postgresql` 16.3 image on `nwa02`. Those belong to other workloads. The Keycloak database is the PostgreSQL 15 one on `postgresql-db-0`.


- **Service:** `postgres-db` at `10.102.17.175:5432`, in the Keycloak namespace.
- **Pod:** `postgresql-db-0`, currently on `nwa03`.
- **Database:** `keycloak`.
- **Login:** role `keycloak`. The Keycloak deployment reads its credentials from `KC_DB_USERNAME` and `KC_DB_PASSWORD`.

**Known problem:** the running Keycloak container has `KC_DB_USERNAME=error` and `KC_DB_PASSWORD=error`. The secret lookup failed when the container started, so Keycloak has no database login. This needs fixing as part of any restore, and it's the likely cause of the current outage.

## What the database restore brings back

- Users, password hashes, MFA credentials, and sessions.
- Realm settings, clients, client secrets, groups, roles, identity providers, auth flows, and components.
- Realm signing keys. Tokens issued before the outage remain valid after the restore.

## What still needs re-entry

- **Database password:** rotate it as part of the redeploy. The restore needs the new password in the `KC_DB_PASSWORD` secret.
- **Bootstrap admin password:** it was exposed in chat, so rotate it as well.
- **Identity provider secrets and component passwords:** if they're masked in the database too, re-enter them. Check after the restore.

## Procedure: database restore

1. **Stop Keycloak** so nothing writes to the database during the restore. Scale the Keycloak StatefulSet to 0.
2. **Start a clean database** on the new cluster, with the `keycloak` database and role created. Use the new password from the secret store.
3. **Copy the dump** to the node that runs the database, or to a pod that can reach `postgres-db`.
4. **Restore it:**
   ```
   pg_restore --no-owner --role=keycloak -U keycloak -d keycloak --clean --if-exists keycloak-2026-10-21-0307.dump
   ```
5. **Check the restore:**
   ```
   pg_restore --list keycloak-2026-10-21-0307.dump | head
   psql -U keycloak -d keycloak -At -c "select count(*) from user_entity"
   ```
   The count should match the user count in the export (1 user at the time of the dump).
6. **Start Keycloak** with the correct `KC_DB_USERNAME` and `KC_DB_PASSWORD`, and the ITL theme image.
7. **Verify:**
   - The admin console loads at `sts.itlusions.com`, and the `itlusions` realm exists.
   - An existing user can log in with their password and MFA.
   - A test client can get a token, and the token validates against the realm's keys.
   - Client secrets work for confidential clients.

## Procedure: realm import (fallback)

Use this only if the database dump can't be restored.

1. Install Keycloak from the operator, with the ITL theme image.
2. Merge the JSON exports into one realm representation: `realm_settings` at the top level, plus `clients` (with each `secret` set from `client_secrets`), `clientScopes`, `groups`, `roles`, `identityProviders`, `authenticationFlows`, `requiredActions`, `components`, and `users` from the export.
3. Import with a `KeycloakRealmImport` resource, or `kc.sh import` in the pod. Keep the merged file in a Secret, not in git.
4. Re-enter masked identity provider and component secrets.
5. Send each user a password reset, and re-enrol MFA.
6. Expect every client to pick up the new signing keys.

## Test before the real restore

- Restore the dump into the local kind cluster (`kind-itl-prefect`) first, to check the file, the login, and the client flows, without touching production.
- Write down any manual fixes here, so the production restore follows the same path.
