# Kubernetes Storage Classes Documentation

This directory contains documentation for all storage classes available in the ITL Kubernetes cluster.

> **Live status (confirmed via `kubectl get storageclass`):** only the eight Longhorn-backed classes below are currently deployed - `longhorn`, `ha-dbs-lh`, `ha-gen-lh`, `ha-perf-lh`, `ha-secure-lh`, `ha-grafana-block`, `dev-single-lh`, `longhorn-static`. They ship from [`ITL.Longhorn`](https://github.com/ITlusions/ITL.Longhorn)'s `templates/storageclasses/` (see that repo's `docs/1-longhorn/1.3-storage-classes.md` for a shorter version of the same reference). `minio-data`, `nfs-csi`, `openebs-hostpath`, and `local-storage` below are **not currently deployed** - kept here as a reference for provisioners outside Longhorn should they be needed.

## Overview

Storage classes define different types of storage that can be dynamically provisioned for applications. Each storage class has specific characteristics, performance profiles, and use cases.

## Available Storage Classes

### Production Storage Classes

#### 1. **ha-dbs-lh** - High Availability Database Storage
- **File**: `ha-dbs-lh.yaml`
- **Purpose**: Production database storage with high availability
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Replicas**: 3 (across different nodes)
- **Reclaim Policy**: Retain (data preserved even if PVC deleted)
- **Volume Expansion**: ✅ Supported
- **Use Cases**: 
  - PostgreSQL databases (like CNPG clusters)
  - MySQL/MariaDB production instances
  - MongoDB replica sets
  - Any critical database requiring data persistence

#### 2. **ha-gen-lh** - General High Availability Storage
- **File**: `ha-gen-lh.yaml`
- **Purpose**: Balanced high availability with good performance
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Replicas**: 2 (optimized balance of availability and performance)
- **Reclaim Policy**: Retain (data preserved)
- **Volume Expansion**: ✅ Supported
- **Use Cases**:
  - General application storage requiring HA
  - Monitoring systems (Prometheus, Grafana)
  - Application data with moderate criticality
  - Balanced performance and availability needs

#### 3. **ha-perf-lh** - High Performance Storage
- **File**: `ha-perf-lh.yaml`
- **Purpose**: Optimized for high performance workloads
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Replicas**: 2 (fast replication)
- **Timeout**: 20 seconds (faster than standard)
- **Data Locality**: Best-effort (keeps data close to workload)
- **Reclaim Policy**: Delete
- **Volume Expansion**: ✅ Supported
- **Use Cases**:
  - High-performance applications
  - Real-time data processing
  - Applications requiring low latency
  - Performance-critical workloads

#### 4. **ha-secure-lh** - Encrypted High Availability Storage 🔐
- **File**: `ha-secure-lh.yaml`
- **Purpose**: Encrypted storage for sensitive data
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Replicas**: 2 with anti-affinity rules (spread across nodes/disks)
- **Encryption**: ✅ LUKS encryption enabled
- **Reclaim Policy**: Retain (encrypted data preserved)
- **Volume Expansion**: ✅ Supported
- **Use Cases**:
  - Sensitive database storage
  - Compliance-required data (GDPR, HIPAA)
  - Financial or healthcare applications
  - Any data requiring encryption at rest

#### 5. **ha-grafana-block** - Block Storage for Grafana 📊
- **File**: `ha-grafana-block.yaml`
- **Purpose**: Raw block storage optimized for Grafana dashboards
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Storage Type**: Raw block device (no filesystem layer)
- **Replicas**: 2 with anti-affinity rules
- **Frontend**: Block device (not filesystem)
- **Data Locality**: Best-effort (performance optimization)
- **Reclaim Policy**: Retain
- **Volume Expansion**: ✅ Supported
- **Use Cases**:
  - Grafana dashboard storage
  - Time-series database storage
  - Applications requiring raw block access
  - High-performance database workloads

#### 6. **longhorn** - Default Distributed Storage
- **File**: `longhorn.yaml`
- **Purpose**: General-purpose distributed storage (cluster default)
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Replicas**: 3 (across different nodes)
- **Reclaim Policy**: Delete
- **Volume Expansion**: ✅ Supported
- **Use Cases**:
  - Application data volumes
  - Non-critical databases
  - General persistent storage needs
  - Default choice for most workloads

### Development & Testing Storage Classes

#### 7. **dev-single-lh** - Development Storage
- **File**: `dev-single-lh.yaml`
- **Purpose**: Fast single-replica storage for development
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Replicas**: 1 (no redundancy, fastest provisioning)
- **Binding**: WaitForFirstConsumer (efficient resource usage)
- **Reclaim Policy**: Delete (automatic cleanup)
- **Volume Expansion**: ✅ Supported
- **Use Cases**:
  - Development environments
  - Testing and CI/CD pipelines
  - Temporary workloads
  - Non-critical single-node applications

### Specialized Storage Classes

#### 8. **minio-data** - Object Storage
- **File**: `minio-data.yaml`
- **Purpose**: Optimized for MinIO object storage
- **Provisioner**: OpenEBS Local (openebs.io/local)
- **Path**: `/mnt/data-lv-01/minio`
- **Reclaim Policy**: Delete
- **Volume Expansion**: ❌ Not supported
- **Use Cases**:
  - MinIO tenant data storage
  - Object storage workloads
  - Large file storage

#### 9. **nfs-csi** - Network File System
- **File**: `nfs-csi.yaml`
- **Purpose**: Shared network storage
- **Provisioner**: NFS CSI (nfs.csi.k8s.io)
- **Server**: 10.99.100.3
- **Share**: `/mnt/data-lv-01`
- **Protocol**: NFSv4.1
- **Volume Expansion**: ❌ Not supported
- **Use Cases**:
  - Shared configuration files
  - Multi-pod read/write access
  - Legacy applications requiring NFS

### Local Storage Classes

#### 10. **openebs-hostpath** - Local Node Storage (Default)
- **File**: `openebs-hostpath.yaml`
- **Purpose**: Fast local storage on each node
- **Provisioner**: OpenEBS Local (openebs.io/local)
- **Path**: `/var/openebs/local`
- **Binding**: WaitForFirstConsumer
- **Volume Expansion**: ❌ Not supported
- **Use Cases**:
  - High-performance applications
  - Temporary storage
  - Single-node applications
  - Cache volumes

#### 11. **longhorn-static** - Simplified Longhorn
- **File**: `longhorn-static.yaml`
- **Purpose**: Basic Longhorn storage with minimal config
- **Provisioner**: Longhorn (driver.longhorn.io)
- **Reclaim Policy**: Delete
- **Volume Expansion**: ✅ Supported
- **Use Cases**:
  - Simple distributed storage needs
  - Pre-provisioned volumes
  - Basic application storage

#### 12. **local-storage** - Manual Provisioning
- **File**: `local-storage.yaml`
- **Purpose**: Manually managed local volumes
- **Provisioner**: None (kubernetes.io/no-provisioner)
- **Binding**: WaitForFirstConsumer
- **Volume Expansion**: ❌ Not supported
- **Use Cases**:
  - Pre-allocated hardware storage
  - Specific node storage requirements
  - Manual storage management

## Storage Class Selection Guide

### For Databases 🗄️
- **Critical Production**: Use `ha-dbs-lh` for mission-critical databases (3 replicas)
- **Secure/Encrypted**: Use `ha-secure-lh` for sensitive data with encryption
- **General Production**: Use `ha-gen-lh` for balanced HA and performance (2 replicas)
- **Development**: Use `dev-single-lh` for fast development databases
- **High Performance**: Use `ha-perf-lh` for performance-critical databases

### For Applications 📱
- **General HA**: Use `ha-gen-lh` for most production applications
- **High Performance**: Use `ha-perf-lh` for performance-critical apps
- **Grafana/Dashboards**: Use `ha-grafana-block` for optimal Grafana performance 📊
- **Secure Apps**: Use `ha-secure-lh` for encrypted application data
- **Development**: Use `dev-single-lh` for fast development cycles
- **Legacy/Default**: Use `longhorn` for existing applications
- **Local Performance**: Use `openebs-hostpath` for single-node apps
- **Shared Data**: Use `nfs-csi` for multi-pod access

### For Object Storage 🗂️
- **MinIO**: Use `minio-data`
- **General Objects**: Use `longhorn`

### For Temporary Storage ⏱️
- **Fast Temporary**: Use `openebs-hostpath`
- **Distributed Temporary**: Use `longhorn`

## Volume Binding Modes

- **Immediate**: Volume is created immediately when PVC is created
- **WaitForFirstConsumer**: Volume creation waits until pod is scheduled

## Reclaim Policies

- **Delete**: PersistentVolume is deleted when PVC is deleted
- **Retain**: PersistentVolume is preserved even after PVC deletion (manual cleanup required)

## Best Practices

### For Production Workloads
1. Use `ha-dbs-lh` for critical databases
2. Use `longhorn` for general application storage
3. Always specify resource limits and requests
4. Monitor storage usage and performance

### For Development
1. Use `longhorn` or `openebs-hostpath` for most cases
2. Consider cleanup policies for temporary environments
3. Use appropriate storage sizes to avoid waste

### For Backup and Disaster Recovery
1. `ha-dbs-lh` with Retain policy for critical data
2. Regular backups regardless of storage class
3. Test restore procedures periodically

## Troubleshooting

### Common Issues
1. **PVC Pending**: Check storage class availability and node resources
2. **Volume Mount Failures**: Verify node labels and storage class parameters
3. **Performance Issues**: Consider storage class characteristics and node resources

### Monitoring
- Monitor PV/PVC status: `kubectl get pv,pvc -A`
- Check storage class details: `kubectl describe storageclass <name>`
- View storage usage: `kubectl top nodes`

## Examples

### Database PVC Example
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: ha-dbs-lh
  resources:
    requests:
      storage: 10Gi
```

### Application PVC Example
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: longhorn
  resources:
    requests:
      storage: 5Gi
```
