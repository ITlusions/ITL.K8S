# 3.3 Hubble UI: internal exposure and OIDC plan

**Status: planned, not yet implemented.** Nothing in this doc exists in the cluster yet. It's the concrete design to build from when this gets picked up, written 2026-10-23.

**Update 2026-10-23:** steps 2-4 below (the `oauth2-proxy` Deployment/Service, the `forwardAuth` Middleware, and the `KeycloakOIDCClient` CR) are now packaged as a reusable Helm library chart, [`ITL.AuthGateway`](https://github.com/ITlusions/ITL.AuthGateway), instead of being hand-rolled per service. The manifests below are kept as-is since they document the exact shapes involved, but building this for real means declaring `itl-authgateway` as a chart dependency and filling in its `authGateway:` values block (see that repo's `README.md` for the full worked Hubble example) rather than copying these YAML blocks directly.

## Why this exists

Hubble UI (`kube-system/hubble-ui`, `ClusterIP` on port 80) shows live, cluster-wide network flow data - every pod-to-pod connection, DNS query, and policy verdict. That's sensitive enough that it shouldn't be public, and it has **no built-in authentication of its own** - it's designed to sit behind a trusted perimeter (normally reached via `kubectl port-forward`). Exposing it via Ingress means the cluster has to provide the access control Hubble UI doesn't.

## Design decisions

- **Internal Traefik instance, not public.** Same trust tier as Longhorn - LAN/VPN only, never internet-reachable. See [1.4 Ingress](../1-cluster/1.4-ingress.md) for the two-instance split. This would be the internal instance's **first real route** - it currently has a Gateway (`traefik-internal/internal`) with zero `HTTPRoute`s attached.
- **Keycloak login on top of network ACL, not instead of it.** The LAN/VPN restriction (the existing `acl` Middleware) stays; OIDC adds a second, independent gate rather than replacing it.
- **`oauth2-proxy` in forward-auth mode**, not reverse-proxy mode - Traefik keeps doing the proxying, `oauth2-proxy` only answers the `/oauth2/auth` check. This matches the pattern already used in `ITL.K8s.ResourceExplorer` (bundles the `oauth2-proxy` chart, `provider = "keycloak-oidc"`, issuer `https://sts.itlusions.com/realms/itlusions`).

## 1. HTTPRoute (internal Gateway)

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: hubble-ui
  namespace: kube-system
  labels:
    itlusions.nl/traefik-instance: internal
spec:
  parentRefs:
    - name: internal
      namespace: traefik-internal
  hostnames:
    - "hubble.k8s.int.itlusions.nl"
  rules:
    - backendRefs:
        - name: hubble-ui
          port: 80
```

Needs: a DNS record (`hubble.k8s.int.itlusions.nl` → `10.99.99.26`, written into the `int.itlusions.nl` zone - see [1.6 DNS](../1-cluster/1.6-dns.md)) and a cert off the existing `internal-tls` DNS-01 setup. **Open item:** confirm the exact `ExtensionRef` filter syntax this Traefik chart version (42.1.3) uses to attach a `Middleware` to an `HTTPRoute` - verify with `helm template` before applying, rather than assuming parity with the Ingress-annotation syntax used elsewhere in this repo.

## 2. Keycloak client

The cluster has a live Keycloak Operator (`itl-keycloak` CR, namespace `itl-keycloak`, realm `itlusions`), but its actual client CRD is `KeycloakOIDCClient` (`k8s.keycloak.org/v2alpha1`) - **not** `KeycloakClient`, which is what `itl.website`'s `charts/itl.website/templates/keycloak-client.yaml` incorrectly assumes (found as a side effect of this investigation; harmless today only because that chart's `keycloak.createClient` is `false`, so the template has never actually been applied - itl-website's real client was restored by hand from the old pg_dump instead). Worth fixing separately, unrelated to Hubble.

The correct shape, confirmed against the live CRD schema:

```yaml
apiVersion: k8s.keycloak.org/v2alpha1
kind: KeycloakOIDCClient
metadata:
  name: hubble-ui
  namespace: itl-keycloak        # must be the Keycloak CR's own namespace
spec:
  keycloakCRName: itl-keycloak
  realm: itlusions
  client:
    displayName: "Hubble UI"
    description: "Cilium network flow observability"
    enabled: true
    loginFlows: ["STANDARD"]
    redirectUris:
      - "https://hubble.k8s.int.itlusions.nl/oauth2/callback"
    webOrigins:
      - "https://hubble.k8s.int.itlusions.nl"
    auth:
      method: client-secret
      secretRef:
        name: hubble-ui-oidc-secret
        key: client-secret
```

**Open item:** confirm whether the operator generates `hubble-ui-oidc-secret` itself when `secretRef` points at a Secret that doesn't exist yet, or expects it pre-created - this determines apply order (client CR first vs. Secret first). No existing `KeycloakOIDCClient` resource exists in the cluster yet to check the pattern against, so this needs a small test against a throwaway client before relying on it for real.

## 3. `oauth2-proxy`

New Deployment + Service (namespace TBD - either `kube-system` alongside Hubble, or a new dedicated namespace; leaning toward a dedicated namespace if this pattern gets reused for other internal dashboards later). Config:

```
provider = "keycloak-oidc"
oidc_issuer_url = "https://sts.itlusions.com/realms/itlusions"
upstreams = ["http://hubble-ui.kube-system.svc.cluster.local:80"]
email_domains = ["itlusions.com", "itlusions.nl"]
cookie_secure = true
pass_access_token = true
```

Run with `--upstream=static://202` (forward-auth mode - see above), client ID/secret sourced from the `hubble-ui-oidc-secret` Secret from step 2.

## 4. Traefik forwardAuth Middleware

```yaml
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata:
  name: hubble-oidc-auth
  namespace: kube-system
spec:
  forwardAuth:
    address: "http://oauth2-proxy.kube-system.svc.cluster.local:4180/oauth2/auth"
    trustForwardHeader: true
    authResponseHeaders:
      - X-Auth-Request-User
      - X-Auth-Request-Email
      - Authorization
```

Attached to the `HTTPRoute` from step 1 via `ExtensionRef`, alongside the existing `acl` Middleware - end state is LAN/VPN **and** a valid Keycloak session both required.

## Build order

1. `oauth2-proxy` Deployment + Service (nothing depends on it being reachable externally yet).
2. `KeycloakOIDCClient` - test the secret-handling behavior with this one before assuming the pattern for anything else.
3. `forwardAuth` Middleware, once the client secret exists and `oauth2-proxy` is actually configured with it.
4. `HTTPRoute` + DNS record + cert last, once the auth chain in front of it works end to end.
