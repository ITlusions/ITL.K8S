# Break Glass Access - Emergency Cluster Access


> 🚨 **Emergency procedures for Kubernetes cluster access when normal authentication fails**

## Overview

Break glass access provides emergency cluster access through a pre-existing emergency admin user when normal authentication systems (GitHub OAuth, Keycloak) are unavailable.

## 🔑 Access Method

### Tiered Emergency Access Approach

Our break glass access uses a **multi-tier approach** for maximum reliability:

**Tier 1: Emergency Admin Accounts in Keycloak**
- Pre-configured emergency admin users in Keycloak
- Independent of GitHub OAuth (local Keycloak accounts)
- Can be used when GitHub is down but Keycloak is still accessible

**Tier 2: Node-stored Configuration**
- Emergency kubeconfig files stored directly on cluster nodes
- Used when both GitHub OAuth AND Keycloak are unavailable
- Platform engineers access nodes directly to retrieve credentials

**Tier 3: Vault Backup**
- Credentials securely stored in HashiCorp Vault as final fallback
- Independent backup when all other methods fail

## 🏗️ Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                Emergency Access Hierarchy                   │
└─────────────────────────────────────────────────────────────┘

GitHub OAuth Fails
       ↓
Tier 1: Emergency Keycloak Admin → Direct Keycloak Login
       ↓ (if Keycloak also fails)
Tier 2: Platform Engineer → Physical Node Access → Emergency Kubeconfig
       ↓ (if nodes unavailable)
Tier 3: Vault Retrieval → Emergency Credentials
       ↓
   kubectl commands with cluster-admin privileges
```

## 📂 Implementation Details

### Tier 1: Emergency Keycloak Accounts

```yaml
# Emergency admin users in Keycloak (local accounts, not GitHub-linked)
Users:
  - emergency-admin-1@itlusions.local
  - emergency-admin-2@itlusions.local
  - emergency-admin-platform@itlusions.local

# Keycloak Group Mapping
Groups:
  - emergency-admins → kubernetes-cluster-admins

# These accounts bypass GitHub OAuth completely
# Can authenticate directly to Keycloak when GitHub is down
```

### Tier 2: Emergency Kubernetes User

```yaml
# Emergency admin user (pre-created)
apiVersion: v1
kind: ServiceAccount
metadata:
  name: emergency-admin
  namespace: kube-system
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: emergency-admin-binding
subjects:
- kind: ServiceAccount
  name: emergency-admin
  namespace: kube-system
roleRef:
  kind: ClusterRole
  name: cluster-admin
  apiGroup: rbac.authorization.k8s.io
```

### Node Storage Locations

Emergency kubeconfig files are stored on each control plane node:

```bash
# Primary location
/etc/kubernetes/emergency/emergency-admin.kubeconfig

# Backup location
/opt/kubernetes/emergency/emergency-admin.kubeconfig

# Permissions: 600 (readable only by root)
```

### Vault Storage

Credentials are also stored in HashiCorp Vault:

```bash
# Vault path
secret/kubernetes/emergency-access/

# Contains:
# - emergency-admin.kubeconfig (base64 encoded)
# - service-account-token
# - cluster-ca-certificate
# - emergency-contact-procedures
```

## 🚨 Emergency Access Procedure

### Step 1: Determine Emergency Situation

**Use break glass access only when:**
- GitHub OAuth authentication is down
- All normal GitHub-linked admin accounts are inaccessible
- Critical incident requires immediate cluster access
- Normal authentication methods are compromised

### Step 2: Try Tier 1 - Emergency Keycloak Accounts

```bash
# First attempt: Use emergency Keycloak admin accounts
# These are local Keycloak accounts, not linked to GitHub

# Login using kubectl with OIDC (pointing to Keycloak directly)
kubectl oidc-login \
  --oidc-issuer-url=https://auth.k8s.itlusions.com/realms/kubernetes \
  --oidc-client-id=kubernetes \
  --oidc-username-claim=preferred_username \
  --oidc-groups-claim=groups

# Use emergency admin credentials:
# Username: emergency-admin-1@itlusions.local
# Password: [stored in secure location]

# Verify access
kubectl auth whoami
# Expected: emergency-admin-1@itlusions.local

# Test cluster access
kubectl get nodes
kubectl get pods --all-namespaces
```

### Step 3: Tier 2 - Physical Node Access (if Keycloak fails)

```bash
# If Keycloak is also unavailable, use node-stored config
# SSH to any control plane node
ssh platform-engineer@control-plane-node-01

# Switch to root (if needed)
sudo su -

# Navigate to emergency config location
cd /etc/kubernetes/emergency/
```

### Step 4: Activate Emergency Kubeconfig

```bash
# Use emergency kubeconfig
export KUBECONFIG=/etc/kubernetes/emergency/emergency-admin.kubeconfig

# Verify access
kubectl auth whoami
# Expected output: system:serviceaccount:kube-system:emergency-admin

# Test cluster access
kubectl get nodes
kubectl get pods --all-namespaces
```

### Step 5: Tier 3 - Vault Access (final fallback)

If node access is unavailable:

```bash
# Retrieve from Vault (if accessible)
vault kv get -field=kubeconfig secret/kubernetes/emergency-access > emergency.kubeconfig

# Use retrieved config
export KUBECONFIG=./emergency.kubeconfig
kubectl get nodes
```

## 🔒 Security Controls

### Access Restrictions

- **Physical Access Required**: Emergency config only on control plane nodes
- **Root Privileges**: Files require root access on nodes
- **Platform Engineer Access**: Only platform engineers have node SSH access
- **Vault ACLs**: Vault emergency path restricted to emergency group

### Audit Trail

```bash
# All emergency access is logged
kubectl logs -n kube-system deployment/audit-webhook
grep "emergency-admin" /var/log/kubernetes/audit.log

# Emergency usage tracking
tail -f /var/log/emergency-access.log
```

### Time-Limited Usage

```bash
# Emergency access should be temporary
# After incident resolution, rotate credentials:

# 1. Create new emergency service account
kubectl create serviceaccount emergency-admin-new -n kube-system

# 2. Update kubeconfig files
# 3. Update Vault storage
# 4. Delete old service account
kubectl delete serviceaccount emergency-admin -n kube-system
```

## 📋 Emergency Scenarios

### Scenario 1: GitHub OAuth Down, Keycloak Available

```bash
# GitHub authentication unavailable
# Keycloak still accessible

# Use Tier 1: Emergency Keycloak accounts
kubectl oidc-login \
  --oidc-issuer-url=https://auth.k8s.itlusions.com/realms/kubernetes \
  --oidc-client-id=kubernetes

# Login with: emergency-admin-1@itlusions.local
# Check cluster status
kubectl get pods -n keycloak  # Verify systems
kubectl get events --sort-by='.lastTimestamp'
```

### Scenario 2: Both GitHub and Keycloak Down

```bash
# Both authentication providers unavailable
# Need physical access to nodes

# Use Tier 2: Node-stored emergency config
ssh control-plane-01
export KUBECONFIG=/etc/kubernetes/emergency/emergency-admin.kubeconfig
kubectl get pods -n keycloak  # Check Keycloak status
kubectl logs -n keycloak deployment/keycloak  # Investigate issue
```

### Scenario 3: All Admin Accounts Locked

```bash
# All GitHub admin accounts compromised/locked
# Emergency Keycloak accounts still available

# Try Tier 1 first:
kubectl oidc-login  # Use emergency-admin-1@itlusions.local
kubectl get events --sort-by='.lastTimestamp'  # Check recent events
kubectl delete pod suspicious-pod  # Take immediate action

# If Keycloak also compromised, use Tier 2:
# Emergency access via node-stored config
export KUBECONFIG=/etc/kubernetes/emergency/emergency-admin.kubeconfig
kubectl delete deployment malicious-deployment
```

### Scenario 4: Cluster Security Incident

```bash
# Suspected security breach
# Need immediate containment

# Emergency response:
export KUBECONFIG=/etc/kubernetes/emergency/emergency-admin.kubeconfig
kubectl get pods --all-namespaces -o wide | grep "unknown-image"
kubectl delete deployment malicious-deployment
kubectl apply -f security-networkpolicy.yaml
```

## 🔧 Maintenance Procedures

### Regular Testing

```bash
# Monthly test (during maintenance window)

# Test Tier 1: Emergency Keycloak accounts
kubectl oidc-login  # Test emergency-admin-1@itlusions.local login
kubectl auth can-i '*' '*'  # Should return "yes"

# Test Tier 2: Node-stored emergency access
export KUBECONFIG=/etc/kubernetes/emergency/emergency-admin.kubeconfig
kubectl auth can-i '*' '*'  # Should return "yes"

# Test Tier 3: Vault backup
vault kv get secret/kubernetes/emergency-access

# Update documentation if needed
```

### Credential Rotation

```bash
# Quarterly credential rotation
# 1. Create new service account token
kubectl create token emergency-admin --duration=0  # Non-expiring token

# 2. Update kubeconfig files on all nodes
ansible-playbook update-emergency-kubeconfig.yml

# 3. Update Vault storage
vault kv put secret/kubernetes/emergency-access kubeconfig=@new-emergency.kubeconfig

# 4. Test new credentials
# 5. Revoke old tokens (if possible)
```

## 📝 Post-Incident Procedures

### After Emergency Access Usage

1. **Document the Incident**: Record what happened, why emergency access was needed
2. **Review Actions Taken**: Document all kubectl commands executed
3. **Security Review**: Ensure no unauthorized changes were made
4. **Credential Rotation**: Consider rotating emergency credentials after use
5. **Process Improvement**: Update procedures based on lessons learned
