# 3.4 Personas, Keycloak groups, and app-level roles

**Status: draft, no real people assigned yet.** Written 2026-10-23 while standing up [`ITL.Headscale`](https://github.com/ITlusions/ITL.Headscale)'s access control - `oidc.allowedGroups` needed a real answer, which surfaced the fact that there was no single place documenting who should get what, across every Keycloak-gated thing in this cluster. This is that place. Fill in real names/emails per persona yourself - this doc deliberately doesn't invent them.

## Why this exists

Every piece built this session that uses Keycloak OIDC (`ITL.Headscale`, `ITL.Headscale.UI`/Headplane, the [Hubble UI plan](3.3-hubble-ui-oidc-plan.md), `ITL.AuthGateway`, the website) makes its own access decision independently - a group name picked ad hoc, per chart. That's already started drifting: `/vpn-users` exists because Headscale needed *an* answer right now, not because it was planned against the other apps. This doc is the map those per-app decisions should reference going forward, not a new system to build.

## Personas

| Persona | Who this is | What they need |
|---|---|---|
| **Platform admin** | Runs the cluster - deploys charts, manages Keycloak, rotates secrets, has `kubectl`/`talosctl` access already (outside Keycloak entirely - that's kubeconfig/talosconfig, not OIDC) | Everything: VPN access to all ranges, Headplane `admin` role, Hubble UI (once built), Longhorn UI |
| **Remote collaborator** | Someone who needs to reach specific cluster-internal resources from off-LAN, but isn't operating the cluster | VPN access, scoped - not necessarily every range `ITL.Wireguard`/`ITL.Headscale` currently grant everyone. See "Open item: tiered VPN access" below - today there's no tier below "full access," which is too broad for this persona. |
| **Auditor / reviewer** | Needs to see what's happening (flows, logs, config) without being able to change anything | Hubble UI read access, Headplane `auditor` role, no VPN write/manage capability, no Longhorn write access |
| **Automation / CI-CD** | Not a human, not OIDC at all - service accounts, deploy keys, kubeconfig tokens | Out of scope for this doc on purpose - don't route machine identities through Keycloak groups meant for humans |

## Keycloak groups (realm `itlusions`)

| Group | Maps to persona | Status |
|---|---|---|
| `/vpn-users` | Remote collaborator (today: everyone with VPN access, not yet tiered) | **Exists** - created 2026-10-23 for `ITL.Headscale`'s `oidc.allowedGroups` |
| `/platform-admins` | Platform admin | **Not created yet** - needed before `ITL.Headscale.UI`'s `default_role`/`role_claim` mapping means anything real |
| `/auditors` | Auditor / reviewer | **Not created yet** |

Decide now whether `/platform-admins` members also need separate membership in `/vpn-users` (Keycloak groups don't nest permissions automatically - a user in `/platform-admins` but not `/vpn-users` won't pass Headscale's `allowed_groups` check unless that's explicitly accounted for, either by dual membership or by adding `/platform-admins` to Headscale's `allowed_groups` list too).

## Per-application mapping

| App | Mechanism | Group(s) currently wired | Status |
|---|---|---|---|
| `ITL.Headscale` (tailnet join) | `oidc.allowedGroups` in `values.yaml` | `/vpn-users` | Set, not yet live - blocked on the `client-admin-api:v2` Keycloak feature flag (see below) |
| `ITL.Headscale.UI` (Headplane admin UI) | `role_claim: headplane_role` → one of `admin`/`network_admin`/`it_admin`/`auditor`/`viewer`/`member` | **Not mapped yet** | Headplane expects a custom `headplane_role` claim in the token - Keycloak needs a protocol mapper translating group membership into that claim's value. Not built. See open item below. |
| Hubble UI (planned, [3.3](3.3-hubble-ui-oidc-plan.md)) | `ITL.AuthGateway`'s `oauth2Proxy.allowedGroups` | Not decided | Plan doc currently shows `["platform-engineers"]` as an example only - rename to match this doc's `/platform-admins` once that group exists, don't leave the two inconsistent |
| ITL website login | Standard Keycloak login, no group restriction currently | n/a | Any realm user can log in - different risk profile (public-facing signup-style app, not infra access) |
| Keycloak admin console itself | Keycloak's own built-in realm-admin roles | n/a | Separate from this doc's groups entirely - don't conflate "can manage Keycloak" with "can join the VPN" |

## Open items

- **Blocking right now**: the Keycloak instance doesn't have the `client-admin-api:v2` feature enabled, so the `KeycloakOIDCClient` CRD can't create any client at all yet (both `headscale` and `headplane` CRs are currently stuck in an error state for this reason, unrelated to anything in this doc). Nothing here is live until that's resolved.
- **`/platform-admins` and `/auditors` don't exist yet** - create them in the Keycloak admin console before assigning anyone.
- **No protocol mapper exists for `headplane_role`** - needs a Keycloak client-scope mapper (group-membership → claim value) added to the `headplane` client once it can actually be created.
- **Tiered VPN access isn't designed** - today, `allowedGroups` is a single yes/no gate; a "remote collaborator" and a "platform admin" get identical network reach once in `/vpn-users`. If that's too broad for a collaborator persona, that needs either a second Headscale ACL policy (Headscale supports per-user/per-group ACL rules, not just a login allowlist - not yet configured) or a second, narrower group.
- **No real people assigned to any group yet** - this doc is the structure, not the roster.
